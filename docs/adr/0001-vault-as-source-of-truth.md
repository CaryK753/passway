# ADR-0001：以 Obsidian Vault 作为唯一内容事实源

## 状态

Superseded by ADR-0004

## 日期

2026-09-08

> 本文保留为早期决策记录。当前采用普通 Markdown + GitHub 事实源，详见 [ADR-0004](0004-github-content-and-weknora-derived-knowledge.md)。

## 背景

Passway 需要同时满足内容可读、社区可贡献、关系可表达、变更可审核、历史可追踪和 AI 可检索。若 Markdown 与数据库都能独立修改同一事实，将产生双向同步和来源漂移。

## 决策驱动因素

- 内容必须可以脱离网站在 Obsidian 中使用。
- 所有关系应以文件级链接表达并接受断链检查。
- 贡献和审核应建立在可读 diff 上。
- 索引、数据库或供应商故障不能导致知识资产丢失。
- 派生系统必须可重建。

## 考虑的方案

### 方案 A：Vault 为事实源

优点：开放、可移植、适合审核、天然支持 Obsidian。缺点：需要严格 schema、解析器和发布流水线。

### 方案 B：Supabase 为事实源，导出 Markdown

优点：结构化编辑和查询方便。缺点：Markdown 成为滞后的副本，社区贡献与文件关系不再可靠。

### 方案 C：Vault 与数据库双向编辑

优点：两端都灵活。缺点：冲突解决、ID 稳定和历史归属复杂度过高。

## 决策

选择方案 A。Vault 中经过校验的 Markdown 是唯一内容事实源。Supabase、全文索引、向量和图表均为特定内容快照的派生投影。

## 后果

### 正面

- 可通过 Git 和文件历史审计政策变更。
- 可从 Vault 完整重建线上数据。
- Obsidian 和网站共享同一知识模型。
- 降低对数据库和 AI 供应商的锁定。

### 负面

- 内容写作者必须遵循 schema。
- 发布前需要全量关系校验。
- 高并发线上查询不能直接读取 iCloud 文件，需要快照和数据库投影。

### 风险与缓解

- iCloud 同步中间态可能导致读取不完整：只从明确生成且校验通过的快照发布。
- 文件重命名可能破坏关系：使用稳定 `id`，并由工具完成重命名与链接迁移。
