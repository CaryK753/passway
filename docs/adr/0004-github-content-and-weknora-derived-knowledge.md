# ADR-0004：GitHub 文章事实源与 WeKnora 派生知识

## 状态

Accepted

## 日期

2026-09-09

## 背景

早期方案要求作者在 Obsidian Vault 中把国家、路径、条件、来源和概念拆成大量文件，并由 Passway 自建图投影、混合检索和 Graph RAG。真实内容导入表明，这种方式显著增加写作、复核、迁移和工程维护成本。

WeKnora 已提供知识导入、解析、混合检索、知识问答、Auto-Wiki、Wiki 页面链接图和 Web Embed。Passway 的核心差异应集中在可信移民文章、政策治理和公开阅读体验，而不是重复实现通用 RAG 基础设施。

## 决策

1. GitHub `main` 中通过发布校验的普通 Markdown 文章，是 Passway 人工内容的唯一事实源。
2. 本地目录用于写作与预览；GitHub 负责版本历史、评审、协作和已发布状态。个人 iCloud 目录不是生产依赖。
3. WeKnora 保存由人工文章同步得到的知识条目、分块、向量、Auto-Wiki、页面链接图和实体关系图。这些数据均可删除并重建，不得反向覆盖人工文章。
4. Passway 通过独立 Adapter 调用 WeKnora API。浏览器不直接持有管理 API Key。
5. Next.js 直接呈现人工文章，并通过服务端读取 WeKnora 生成的 Wiki、图谱与问答结果。
6. Supabase 仅在确有需要时保存匿名配额、反馈、公开统计和产品状态，不重复建设 WeKnora 已承担的向量或图索引。

## 内容最小契约

文章保持面向人类的完整叙述，只要求稳定身份、发布状态、法域、时间和来源等少量元数据。内容不再为了构图强制拆成细粒度实体文件，也不要求作者维护完整双向链接。

## 同步原则

- 使用稳定 `content_id` 关联 Git 文件与 WeKnora knowledge ID。
- 使用规范化正文哈希判断新增和变更。
- 删除必须通过 Git 中的显式删除和同步计划确认，不能因临时目录不可用而推断。
- 只有 GitHub `main` 中满足发布条件的文章进入生产知识库。
- 同步过程必须幂等、可预览、可审计，并在部分失败时保留上一个可用状态。
- API 返回成功不等于发布成功；必须继续验证解析、检索、Wiki 和图谱状态。

## 图谱语义

WeKnora 存在两个不同投影：

- Wiki 页面链接图：Auto-Wiki 页面之间的链接和反向链接，主要用于浏览与解释；
- 实体关系知识图谱：从知识中抽取的实体与关系，主要用于检索增强。

Passway MVP 优先呈现 Wiki 页面链接图。实体关系图只有在 API 稳定、质量评测和性能门槛通过后才公开。

## 后果

### 正面

- 作者可用普通 Markdown 写作，内容可读性和贡献门槛更低。
- 减少自建 parser、chunker、embedding、图数据库和 RAG 编排。
- 人工知识不被供应商数据库锁定，WeKnora 可从 Git 快照重建。
- 前端仍能提供文章、AI Wiki、图谱和免登录问答的一体化体验。

### 负面

- Git 内容与 WeKnora 派生状态之间需要可靠的增量同步工具。
- Auto-Wiki 和抽取图谱不是人工核验事实，必须明确标识。
- WeKnora 的 API、任务行为或版本变化可能影响同步与前端读取。
- API 上传后触发 Wiki/图谱更新的行为必须由 PoC 实测，不能仅依赖接口存在。

## 取代关系

本 ADR 取代 ADR-0001、ADR-0002 和 ADR-0003 中有关细粒度 Obsidian 图谱、自建 Graph RAG、生产读取个人 Vault 的决策。旧 ADR 作为历史保留。
