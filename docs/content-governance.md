# 内容治理

## 1. 目标

内容治理确保“已发布、已核验”是一种有证据的状态，而不是作者主观判断。治理覆盖发现、研究、撰写、复核、发布、监测、修订、冲突与撤回。

## 2. 角色

早期团队允许一人兼任多个角色，但同一条重要路径的作者与最终复核者原则上不能是同一人。

| 角色 | 责任 | 不得单独完成 |
| --- | --- | --- |
| Researcher | 查找官方来源、记录适用范围和生效时间 | 宣布内容已核验 |
| Author | 编写文章、对应来源、时效和通俗解释 | 跳过来源直接发布 |
| Reviewer | 逐项核对结论、关系、时效和措辞 | 复核自己撰写的高风险内容 |
| Maintainer | 合并、发布快照、处理紧急撤回 | 用技术权限替代内容证据 |
| Domain Expert | 处理法律歧义、冲突与复杂例外 | 为未经记录的口头意见背书 |

## 3. 内容生命周期

```text
draft
  → in-review
    → verified + published
      → stale
        → in-review → verified
      → conflicted
        → in-review → verified
      → archived
```

- `draft`：允许不完整，但不能用于 AI 确定性回答。
- `in-review`：来源和正文已齐备，等待独立复核。
- `verified`：结论、关系、时间和来源已按清单复核。
- `stale`：超过复核周期或检测到来源变化。
- `conflicted`：可靠来源之间存在无法自动消解的冲突。
- `archived`：路径或来源不再适用，仍保留历史查询价值。

## 4. 创建流程

1. **登记范围**：明确法域、路径名称、目标身份和时间范围。
2. **建立来源卡片**：优先法律、主管机关指引、官方表格和正式统计。
3. **建立文章**：使用稳定 `content_id`、最小 frontmatter 和可读正文。
4. **对应政策声明**：硬性结论在正文附近关联能够直接支持它的来源。
5. **记录不确定性**：未知、例外和冲突不写成笼统肯定句。
6. **运行校验**：schema、断链、来源、时间和重复 ID 全部通过。
7. **提交复核**：附变更摘要、受影响文章和来源清单。
8. **独立复核**：逐条比对原始来源，并检查解释是否超出原文。
9. **同步发布**：只有通过复核的 Git commit 才能进入公开站点和生产 WeKnora 知识库。

## 5. 来源研究规则

- 主管机关和法律文本优先于搜索摘要、媒体和论坛。
- 搜索工具用于发现来源，不直接成为政策依据。
- 同一页面包含多个政策版本时，必须定位具体生效段落。
- 自动翻译只能辅助理解；关键术语保留原文并记录译法。
- 无法访问的页面不能凭缓存摘要继续标记为最新已核验。
- 第三方申请中心只能支撑预约、递交和操作流程，除非主管机关明确授权其发布规则。

## 6. 复核清单

Reviewer 至少回答：

- [ ] 标题、法域和路径身份是否准确？
- [ ] 每条硬性结论是否有足够等级的来源？
- [ ] 引用是否真正支持对应结论，而不只是主题相关？
- [ ] 金额、年限、年龄、语言和积分是否有生效区间？
- [ ] 申请地点、国籍、现有身份和家属条件是否被遗漏？
- [ ] `REQUIRES`、`EXCLUDES`、`ALTERNATIVE_TO` 和 `CAN_TRANSITION_TO` 是否被正确区分？
- [ ] 是否把可能性、自由裁量或例外写成保证？
- [ ] 与相邻路径或历史版本是否出现未解释冲突？
- [ ] 普通读者是否能理解，同时不损失必要限定条件？

## 7. 新鲜度策略

复核周期不是“规则仍然有效”的证明，只是触发重新检查的上限。初始建议：

| 内容 | 最大复核间隔 | 额外触发条件 |
| --- | --- | --- |
| 年度金额、配额、积分线 | 90 天 | 新财年、预算或主管机关公告 |
| 资格要求、许可权利 | 180 天 | 法案、法规、正式政策变更 |
| 申请流程、表格、费用 | 90 天 | 页面、表格版本或支付系统变化 |
| 永居与入籍规则 | 180 天 | 法律修订或判例影响 |
| 一般概念和历史说明 | 365 天 | 被依赖页面发生变化 |

这些是 Phase 1 的起始假设，必须根据变更频率调整。来源内容 hash、HTTP 状态、标题或更新时间变化只触发复核，不能自动改写政策结论。

## 8. 变更影响分析

来源发生变化时，系统应沿反向关系找到：

```text
official source
  ← cited by — article
    ← linked from — related articles
      ← used to generate — WeKnora Wiki / graph / answers
```

受影响文章在复核完成前转为 `stale`。如果变化可能导致用户作出错误决定，Maintainer 应将相关文章从生产 WeKnora 知识库立即禁用并重新生成派生 Wiki；人工页面保留醒目警告。

## 9. 冲突处理

当法律、主管机关指引和表格说明不一致时：

1. 保存各自独立来源和准确适用日期；
2. 将相关 claim 标记为 `conflicted`；
3. 说明冲突点，不擅自合并成一个答案；
4. 优先查找更新的正式解释或联系主管机关；
5. 必要时请 Domain Expert 复核；
6. 在解决前，AI 只能陈述冲突和建议核实，不给确定性资格判断。

## 10. 纠错与撤回

- 公开页面提供文件级纠错入口。
- 紧急错误可先从生产证据集撤回，再完成常规修订。
- 撤回必须保留原因、时间、影响范围和替代信息。
- 不通过删除 Git 历史掩盖曾经发布的错误。
- 修复后重新运行受影响的检索与回答测试，而不只检查页面文本。

## 11. 贡献模板

每次内容变更应回答：

```text
变更了什么：
为什么变更：
适用法域和日期：
新增或替换的官方来源：
受影响的文章、Wiki 和问答测试：
仍未解决的问题：
校验和复核证据：
```

## 12. 发布权限

内容合并、快照构建和线上发布是三个不同动作。早期可以由同一 Maintainer 操作，但系统设计必须保留边界和审计记录。任何人都不能绕过失败的 schema、链接、来源或时间校验直接提升为 `verified`。
